# Context Engine product assessment — 13 September 2026

**Assessment:** Context Engine has a credible product foundation and enough functionality to justify a small, assisted alpha. Its implementation is ahead of its everyday user experience. The immediate investment should connect and simplify the workflows already built, establish dependable operation on the pilot machines, and test whether the context improves actual coding work. The evidence does not yet support a broad, self-service alpha or claims of better task outcomes or lower agent costs.

This assessment examines the actual working tree in `lauracurley/context-engine`, including the portable engine, VS Code extension, package, tests, evaluations and client documentation. Scratch supplied prior decisions and the vendor/client contract; it was not used as proof of implementation. Public comparisons use official documentation retrieved on 13 September 2026. Recommendations below are product judgment for consideration, not newly adopted requirements. No implementation changes accompany this assessment.

The inspected tree contains substantial uncommitted work beyond commit `fec84ca`. The VSIX identifies itself as 0.5.1; its SHA-256 is `0ac2a47852d5bdd12518fbf1399f83e5f7ed0ce1c33259af120079bbc2857ac9`. Forty packaged Python/JavaScript source files matched their working-tree counterparts. Current verification and targeted observations are recorded in the [assessment evidence](../evaluation/product-assessment-2026-09-13.json).

**The product promise should be specific.** A useful positioning statement is: “Give your coding agent current, cited company context and reviewed team guidance, while your company retains control of that knowledge.” The strongest prospective customer is a team working across repositories, with conventions and decisions that source search alone cannot explain, using an already approved coding agent. The likely champion is a senior developer or team maintainer; the runtime preparer supports installation; individual developers should receive the benefit during ordinary tasks.

There are three jobs to make excellent: understand an unfamiliar part of the system; prepare a change with the relevant contracts, exceptions and checks; preserve a reviewed lesson so another developer or agent benefits later. The product should demonstrate these jobs without requiring users to learn its internal storage model. An empty Scratch template, a graph, an index and a large command catalog do not independently establish recurring value.

The commercial hypothesis is that clients will value controlled deployment, portable knowledge and fewer repeated explanations enough to support a maintained product. That remains a hypothesis: there is no willingness-to-pay or client task-success evidence in the material examined. Packaging and support effort will matter to that proposition. A client that only needs one-repository search and a short `AGENTS.md` may have little reason to add this product.

The defensible position is a combination of capabilities and deployment choices. It should be tested against the client's ordinary agent with native search and existing repository instructions. Outperforming a deliberately simple literal-search fixture is a weaker product claim.

**The most consequential alpha fixes are workflow continuity and truthful status.** I would prioritize the following before an unattended client trial. A facilitated internal walkthrough can begin sooner.

| Priority | Finding and user consequence | Smallest useful completion |
| --- | --- | --- |
| A1 | **The task-pack handoff is incompatible with managed pilot mode.** `controller.js` routes handoff to `hooks.agent`; `extension.js` rejects terminal agent flows when `policyPath` is set. The UI still offers “Open agent with pack.” | Provide a supported IDE path: validate and save the local pack, then make its task/evidence available to the existing approved agent, with a clear attachment or copyable handoff fallback. A future read-only pack MCP tool is another option. Do not unblock terminal flows merely to make the button work. |
| A2 | **Ordinary settings changes can look like lost knowledge.** A synthetic test changing only `crawler.interval` selected a different SQLite store: one approved record in the original, zero in the new store, which was unindexed. The old store was retained. The profile editor also saves a new manifest path, and packs are keyed by manifest path/content. | Explain exactly what a revision preserves before saving and provide return-to-prior-profile recovery. Prefer keeping operational settings outside knowledge identity when repository scope is unchanged. Source/scope changes need explicit transition semantics; never automatically merge Team and Personal knowledge. |
| A3 | **Users cannot easily tell whether they are ready to work.** The status bar is the last explicit check; any save marks it for recheck. Generated workspaces depend on task permission, the captured runtime path and the agent's working folder. A conversation opened in a sibling source may not load this MCP configuration. | Show selected repositories, saved-file freshness, watcher state, runtime/parser readiness and a distinguishable agent-connection check. Offer the relevant repair action. Disclose unsaved-buffer handling. Reuse an existing valid generated workspace when possible. |
| A4 | **The supported build and instructions are hard to identify.** Multiple previews share 0.5.1; MCP still reports 0.1.0. The client readiness runbook names a 0.3.0 VSIX. Some historical acceptance text retains superseded reviewer-policy/shared-approval gates. | Freeze one source/package identity; align product and MCP versions, changelog, actual pilot support matrix and current runbook. **Polish should remove effort from the learning workflow.** A maintainer currently chooses a knowledge type and source, types a supporting path, edits and saves JSON, imports it, supplies the revision, and reviews another JSON document. Build one draft/review surface with citation selection, scope, statement, rationale, exception and source preview. Carry IDs/revisions internally. Keep the explicit review decision. Start with practices and decisions if implementing all five specialized editors at once is too much; the other kinds can retain an advanced editor during the assisted alpha.

Commonplace should be the recognizable knowledge home. Its reading view, proposals and maintenance should be connected. The wiki renderer currently recognizes headings but renders other Markdown lines as escaped paragraph text; citations are not navigable source controls. Add proper lists/code formatting and validated local citation links while retaining the existing restriction on executing authored markup or loading remote resources. This improves usability without weakening the boundary. A static architecture diagram already exists; a larger graph visualization is lower priority than readable relationships and source navigation.

The workbench has useful native-theme styling, labels, focus treatment and a status live region. It also exposes eight search modes, a free-text source ID, a history filter on the general search form, a History tab regardless of the restricted profile, and many actions on each evidence card. There are 46 registered commands; the recently simplified sidebar is a welcome improvement, but the main journeys remain fragmented. Use source pickers, capability-aware controls, one primary action per card and a secondary action menu. Keep search state and provide a route back after preview/expansion. Give “no match,” “not indexed,” “unsupported file,” “stale,” and “omitted by budget” different explanations and next actions. Verify keyboard-only use, narrow windows, themes and error recovery in the actual VS Code host; source-level accessibility affordances are not a completed accessibility assessment.

Coverage also needs a product explanation. The scanner accepts an explicit suffix list and excludes files over 512,000 bytes. Important files such as `Makefile`, `Dockerfile`, `requirements.txt` and Groovy `.gradle` files are not in that default suffix set. An index showing “ready” therefore does not imply complete build-system or repository coverage. Provide an inspectable coverage view and deliberate support for relevant configuration files, especially when adding quality-toolchain discovery. [Scanner](../context_engine/core.py).

**Performance is an alpha uncertainty with a concrete cause to investigate.** The targeted 12-file synthetic fixture measured two full source scans for a search, three for a read, and 63 for a change brief. These are scan counts, not a production latency benchmark. Full scans enumerate and read eligible content, so the result identifies work that can grow with repository size. Share a validated snapshot within a request and retain the final freshness check; evaluate incremental invalidation and periodic reconciliation before adding more indexing technology. Do not trade correct scope/freshness for a faster badge.

The new P1 evaluation passed all six cases for both the baseline and candidate. On the change-with-exception case, the candidate reduced calls from three to one and bytes from 2,528 to 2,419, while median local execution increased from about 962 ms to 1,228 ms. The cross-repository candidate emitted more bytes than its baseline. Three repetitions are directional observations only. This is useful evidence that fewer calls and compact responses do not automatically mean faster tasks or cheaper agent work. Neither model tokens nor model task completion was measured.

**New features worth considering, in order, should strengthen the three user jobs.** Effort is relative (S: bounded interface/adapter; M: coordinated core and UI; L: substantial integration), not a delivery estimate.

| --- | --- | --- | --- |

Reuse existing retrieval and brief tools. Test whether users need fewer manual searches and get the right evidence. |
| 2 · M | **Client quality-toolchain context** | Connects contextual understanding to completing a correct change. The first five connect capabilities already present or narrowly extend them. A hosted index, a vendor-operated model proxy, a new autonomous review swarm, broad employee activity analytics, automatic rule approval, or a second general-purpose agent harness should not be the roadmap response to this assessment. ANN/vector-scale work, exhaustive temporal co-change analysis, a new wiki generator and many new integrations should wait for evidence that they solve the pilot's actual failure modes.

**Alpha testing should evaluate use, continuity and reuse.** Start with one small team, its chosen maintainer, the supported Mac/runtime profile and its existing approved agent. The following are proposed acceptance exercises, not retrospective claims that they passed:

| Exercise | Success to look for |
| --- | --- |
| Fresh client installation | After team runtime preparation, an employee selects repositories, reaches a cited result and uses it with the agent without JSON editing or developer terminal commands. Record interventions and time locally. |
| Ordinary saved-file change and branch switch | Current evidence becomes available predictably; stale evidence is visibly withheld; the user can identify and repair a stopped watcher or stale pack. |
| Representative change | The brief finds the needed contract/test/guidance, preserves an important exception, reports omitted/new/deleted material and supports a correct agent outcome. |
| Capture and reuse | A maintainer drafts/reviews a real lesson; a later task in the right scope receives it, while an unrelated task does not. Measure maintenance effort as well as successful retrieval. |
| Continuity and recovery | A refresh-setting change, extension restart, profile revision and rehearsed upgrade do not leave users believing approved knowledge disappeared. Explicit restore is demonstrated on disposable state. |
| Unsupported/degraded situations | Missing parser, inaccessible source, invalid base, cancellation, no answer and budget exhaustion give understandable outcomes and recovery steps. |
| Second-person Commonplace use | Another client-controlled installation can receive the intended records using the documented local review workflow. Nobody assumes the repository mapping is automatic synchronization. |

For the value test, use roughly 10–20 matched tasks across unfamiliar-code lookup, cross-repository changes, exceptions and stale/missing evidence. This is a small directional pilot, not statistical validation. Hold the agent/model settings and source revisions constant where possible, counterbalance task order, and use a human task rubric plus the client's real verification checks. Measure correctness, missing evidence, repeated explanations, time to first useful result, task completion, interventions and the time needed to maintain knowledge. Choose thresholds before comparing candidates. Voluntary reuse on later tasks is stronger product evidence than a successful scripted demo.

Prepopulate a small number of client-authored, reviewed practices/decisions so the alpha tests knowledge reuse rather than an empty database. Client participants perform company-data evaluation internally; vendor-facing demos and reproductions use synthetic/public material. The existing reports cover six compact retrieval operations and exclude knowledge lookup, task success, onboarding and end-to-end agent timing. They cannot establish adoption, learning benefit, unique users or money saved. Do not silently expand the report schema to obtain those measurements.

**The vendor/client boundary is a design advantage and remains intact in these recommendations.** Local indexes, citations, architecture, prompts/tasks, packs, knowledge, rich diagnostics and evaluation records belong in the client-controlled environment. Explicit integrations may reach the client's approved GitHub/model/services directly under its own accounts; routing through a vendor proxy or account would change the boundary. The vendor receives only the agreed fixed-schema content-free usage report after client vetting and manual sharing. Repository IDs, paths, hashes, prompts, embeddings, review events and free-text support attachments are not acceptable substitutes for aggregate statistics. Support should use public/synthetic reproductions and client-side troubleshooting. [Standing boundary](security/VENDOR-DATA-BOUNDARY.md), [metric registry](security/REVIEWED-USAGE.md).

This does not require new SSO, an approval server, proof of corporate folder ownership or employee surveillance for the small alpha. Local maintainer approval remains sufficient, and explicit existing client policies remain effective. This assessment checked product design and selected implementation paths; it is not a new comprehensive vendor-boundary audit of every dependency, deployment credential or selected external service.

**Verification limits:** The current Python suite passed 108 tests with two optional skips; all 36 JavaScript tests passed using the prepared Python/Node runtime configuration. The six-case P1 evidence evaluation and its branch/stale/deletion checks passed. Earlier attempts needed correction to the extracted Python framework environment and JavaScript working directory; these invocation errors were not attributed to product defects. No new dependencies were installed, product source changed, client repository indexed, account connected, package published or active editor profile modified. The assessment did not rerun the complete lint/format/package quality command, conduct a fresh native VS Code host usability test, or rehearse a fresh company-managed Mac. Those limits prevent a general release-readiness claim.
